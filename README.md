# Pixelforge Studio

## What is it
A Laravel 12 + Vue 3 + Inertia app that generates images through **Pixelforge**, a simulated asynchronous image API. Users see an estimated price before they submit and get live status updates.

- App: https://pixelforge-demo.johnpretsch.com
- Repo: https://github.com/john-pretsch/pixelforge-demo

## How was it built

This was generated using Claude Code / Opus 5.5. The API docs and assessment doc were used as part of the prompting:

- https://pixelforge.promptedit.dev/assessment
- https://pixelforge.promptedit.dev/docs

The code was generated using a mix of planning mode, manual mode and automatic mode. Git diff was used to view the generated additions and changes. This allowed some granularity in the commit history. Normally I would squash some of the commits before pushing, but in this case I'll leave them as they are for transparency. Additional features were added after testing.

## Design considerations

- Allow iteration. Retry with this image includes the image and previous prompt as inputs for another try.
- Reference images from url or local upload.
- Nice responsive Vue front end.
- Sign up/login streamlined. No 2FA, forgot password, etc.
- Authorization/authentication is out of the box from Laravel.

### Manual Testing In UI

Simply walk through the functionality from a web browser and other devices.

- Sign up/login with a new user
- Log in as testadmin1@johnpretsch.com in a different browser profile
- Buy credits and generate an image. Check the webhook events in the dashboard. Check that the cost is correct
- Create generations with triggers for error events: [blocked], [overloaded], [fail], [slow], [duplicate]

#### Error behavior
- Blocked: blocked by content policy, so no further action. 
- Overloaded: add a retry button since there is presumably nothing wrong with the content.
- Fail: can retry if desired. 
- Slow: works as normal from the user's point of view.
- Duplicate: Sends duplicate webhooks which should only be processed once. Should appear to work as normal. Check the dashboard.
- Succeed: the normal path.

## Stretch goals

Both stretch goals are built.

### Balances

- Every user has a credit balance, shown next to the form. **Buy credits** adds a $5, $10 or $25 pack. This is a demo purchase with no payment, and the server accepts only those packs.
- Credits are an append-only ledger (`credit_transactions`), and the balance is the exact `SUM` of it:
  - When you submit, the app **holds** the top of the estimate range.
  - When the generation finishes, the hold is **released**. On success, the exact price is **debited**. Failed generations cost nothing.
- Generate is disabled when the estimate's upper bound is more than your balance. The server checks again while holding a lock on the user row, so two tabs can't spend the same credits.
- Settlement happens in `ApplyProviderState`, in the same locked transaction as the status change. A unique key on (generation, type) stops a duplicate webhook from charging twice.

### Admin report (`/admin/report`)

- For each UTC day and each user, it shows what users were charged, what Pixelforge charged us, and the profit and margin.
- Days are bucketed by `completed_at`, the same way Pixelforge bills. Each day's provider cost is compared exactly (9dp) with `GET /v1/usage`, and any difference is flagged.
- Only admins can see it. Grant access with:

```bash
sudo -u www-data php artisan pixelforge:make-admin you@example.com   # --revoke to remove
```

#### Known discrepancy: 2026-11-17

The report flags 2026-11-17. Pixelforge billed 3 generations ($0.082990000), but the app has a record of only 1 ($0.051512500). The difference, $0.031477500, is exactly the cost of two smoke tests run with the **production** key while the app was being built:

| Pixelforge id | Cost | Origin |
|---|---|---|
| `gen_01M7N8G29M9E60870M9QJ4H2MD` | $0.017070000 | A direct API call that became the test fixture in `tests/Support/PixelforgeFixtures.php` |
| `gen_01M7NF4EPYX36STS9NHJZYRV0H` | $0.014407500 | An app smoke test run against the test database, which is wiped on every test run |

No user was charged for either one. They were left in place on purpose: adding records just to force a match would defeat the point of the reconciliation. Every other day, and every generation in the app, matches `/v1/usage` exactly. Lesson learned: smoke tests use a dev key.
